The platform is already running — an OpenShift cluster with the **OpenShell gateway** on it (Part II). Now you do the interesting part by hand: **create your own agent.**

In OpenShell, an agent is a **sandbox** — a pod the gateway creates, seals in its own private network, and governs with a policy. You ask for one with `openshell sandbox create`. We'll make one that runs **OpenClaw** (the agent framework). We'll go one small step at a time.

## Step 1 — Confirm the gateway is listening

Every command you run talks to the gateway. First check it answers:

```bash
openshell status
```

You want `Status: Connected` and a version. The endpoint is the gateway's in-cluster Service (`http://openshell.<namespace>.svc.cluster.local:8080`) — your lab shell runs inside the cluster, so it talks to the gateway directly; the gateway is deliberately **not** published on a public Route. If it's not connected, see [Troubleshooting](/learn/troubleshooting).

## Step 2 — Look at the policy you'll use

OpenShell is **deny-by-default**: a brand-new sandbox can reach **nothing** on the network. You grant access with a *policy* file. Read the template the repo ships:

```bash
cd ~/nemoclaw-openshift-launchable
cat policies/openclaw-sandbox.yaml
```

Two parts matter. First, the **filesystem/process** block — what the agent may touch on disk and run. Second, `network_policies`: a **map of named rules**, each saying *which binary* may reach *which host*. There are three rules: `in-cluster-registry` (the workshop's private npm registry, for skills), `npm-registry` (public npm, for plugin dependencies) and `websearch` (DuckDuckGo). Each grants its hosts to `node`/`npm` only. That's the whole grant — everything not listed is denied.

```yaml
network_policies:
  in-cluster-registry:
    endpoints:
      - { host: registry.openshell.svc.cluster.local, port: 4873, access: full, protocol: rest, allow_encoded_slash: true }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node }, { path: /usr/bin/npm }, { path: /usr/local/bin/npm } ]
  websearch:
    endpoints:
      - { host: duckduckgo.com, port: 443, access: full }
      - { host: html.duckduckgo.com, port: 443, access: full }
      - { host: lite.duckduckgo.com, port: 443, access: full }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node } ]
```

(In a shared lab the registry host carries *your* namespace — <code>registry.<Ns which="openshell" />.svc.cluster.local</code> — the workshop rewrites it at startup. The OpenShell proxy only matches fully-qualified names, so it's always the full `…svc.cluster.local` form.)

<Callout type="note" title="Where's the inference host?">
Notice there's <strong>no rule for your inference endpoint</strong>. You don't need one: you'll <em>attach the provider</em> you created in the previous lesson (<code>--provider</code>). Its profile composes the inference rule into the sandbox's <em>effective</em> policy — your inference host, <code>node</code>/<code>curl</code> only, with the credential injected on the way out. This file stays about the agent's own tools; you'll see the composed rule with <code>openshell policy get shifty --full</code>.
</Callout>

This policy needs no editing — use it as-is.

## Step 3 — Create the sandbox

One command creates the agent. Let's read each flag, then run it:

- `--name shifty` — what we'll call it.
- `--from "$OPENCLAW_SANDBOX_IMAGE"` — the image: the OpenClaw community sandbox base (`ghcr.io/ansjindal/openclaw-sandbox:2026.8.2`, OpenClaw **2026.8.2**). It ships the `openclaw` agent, `node` and `curl` (DuckDuckGo search is a separate plugin you add in *Give It Web Search*).
- `--policy …/openclaw-sandbox.yaml` — the egress grant from Step 2. **Always pass a policy**: a sandbox created without one never becomes Ready (its supervisor keeps asking the gateway for a policy that isn't there).
- `--provider "$NEMOCLAW_INFERENCE_PROVIDER"` — attach the inference provider from the previous lesson. Inside the sandbox, `$OPENAI_API_KEY` will be a **placeholder**, never your key.
- `--no-tty` — run non-interactively and don't attach a terminal.
- `--detach -- sleep infinity` — the sandbox's **main process**. `sleep infinity` keeps the box up and idle (a command that exits, like `true`, would leave the sandbox *Completed*), and `--detach` makes `create` return as soon as it's running instead of attaching your shell to it. We'll start OpenClaw inside it ourselves in the next lesson.

```bash
openshell sandbox create --name shifty \
  --from "$OPENCLAW_SANDBOX_IMAGE" \
  --policy ~/nemoclaw-openshift-launchable/policies/openclaw-sandbox.yaml \
  --provider "$NEMOCLAW_INFERENCE_PROVIDER" \
  --no-tty --detach -- sleep infinity
```

The gateway writes a `Sandbox` resource, the agent-sandbox controller turns it into a pod, and the gateway starts a **supervisor** for it (the component that seals the network, enforces your policy, and swaps credential placeholders on egress).

Check that the provider is attached:

```bash
openshell sandbox provider list shifty
```

## Step 4 — Wait until it's ready

List your sandboxes:

```bash
openshell sandbox list
```

The pod's container goes ready in seconds, but the gateway needs a moment longer while the supervisor finishes its handshake. The reliable "it's ready" signal is that you can run a command inside it:

```bash
openshell sandbox exec -n shifty -- echo "supervisor ready"
```

When that prints `supervisor ready`, your agent's home is live.

That command went **through the gateway** (`openshell sandbox exec`) — audited and policy-enforced, never a raw `kubectl exec`. The same way, you can run anything inside the box, including the agent's own `openclaw` CLI (it ships in the image):

```bash
openshell sandbox exec -n shifty -- openclaw --version
```

<Callout type="note" title="It's a pod, in the same namespace as the gateway">
<code>oc -n "$OPENSHELL_NS" get pod default--shifty</code> shows it as a normal pod (named <code>default--shifty</code>: the gateway prefixes the workspace, <code>default</code>) — in your <strong><Ns which="openshell" /></strong> namespace, right alongside the gateway (sandboxes are <em>not</em> in a separate namespace). Next to it you'll also see an <code>os-supervisor-…</code> pod: the supervisor the gateway runs for this sandbox. But the agent runs in a <strong>private network namespace</strong> reachable only through the supervisor — that's the seal you'll explore in <a href="/learn/into-the-sandbox">Into a Sandbox</a>.
</Callout>

<Callout type="rh" title="What you just did">
One command, and the gateway turned it into a governed pod on OpenShift — deny-by-default networking, a scoped identity, your policy. Next: give it a brain and start OpenClaw.
</Callout>

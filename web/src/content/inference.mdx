Your agent needs a **brain** — somewhere to send its thinking. It talks to an **OpenAI-compatible inference endpoint** — in this lab, NVIDIA Nemotron 3 Nano served on the cluster's own GPU through OpenShift AI Models-as-a-Service (any remote OpenAI-compatible API works the same way). You provide three things:

- **Base URL** — the endpoint, ending in `/v1` (e.g. `https://api.openai.com/v1`)
- **Model** — the model id to use (e.g. `gpt-4o`)
- **API key** — your provider key (e.g. an `sk-…` key from your provider's dashboard)

<Callout type="note" title="Providers — why your key never enters the agent">
We don't paste the key into the agent. Instead we register the endpoint + key with the <strong>gateway</strong> as a <em>provider</em>, described by a <em>provider profile</em> (which host, which port, which binaries, how the credential is sent). When a sandbox is created with that provider attached, the agent only gets a <strong>placeholder</strong> in <code>$OPENAI_API_KEY</code> (it looks like <code>openshell:resolve:env:v&lt;revision&gt;_OPENAI_API_KEY</code>). The sandbox <strong>supervisor</strong> swaps the placeholder for the real key on egress — only toward the endpoint the profile allows, and only from the binaries it lists. So the agent <strong>never holds your key</strong>, and a leaked placeholder is worthless anywhere else.
</Callout>

<Callout type="rh" title="Shared lab? This is already done for you">
In a facilitated multi-user lab your <code>.env</code> and the gateway provider are pre-configured. Every command below is idempotent — run them anyway to see each piece, nothing breaks.
</Callout>

## Step 1 — Put your values in `.env`

Open the workshop's `.env` in an editor:

```bash
cd ~/nemoclaw-openshift-launchable
nano .env        # or: vi .env
```

Set these three lines (replace the values with your own):

```bash-ref
NEMOCLAW_INFERENCE_BASE_URL=https://api.example.com/v1
NEMOCLAW_MODEL=your-model-id
NEMOCLAW_API_KEY=your-api-key-here
```

Save and exit (in `nano`: <kbd>Ctrl-O</kbd>, <kbd>Enter</kbd>, <kbd>Ctrl-X</kbd>).

## Step 2 — Load them into your shell

```bash
cd ~/nemoclaw-openshift-launchable
set -a; . .env; set +a
echo "URL=$NEMOCLAW_INFERENCE_BASE_URL  MODEL=$NEMOCLAW_MODEL  KEY=${NEMOCLAW_API_KEY:0:6}…"
```

You should see your URL and model, and the key's first few characters (we don't print the whole key).

## Step 3 — Verify the endpoint actually works

Before registering it, sanity-check the endpoint with the standard OpenAI-compatible `/v1/models` call, authenticated with your key:

```bash
curl -sS "$NEMOCLAW_INFERENCE_BASE_URL/models" -H "Authorization: Bearer $NEMOCLAW_API_KEY" | head -c 600; echo
```

A JSON list of models (look for `"object": "list"` and model `"id"`s) means your **endpoint + key are good**. Confirm your chosen model is in the list:

```bash
curl -sS "$NEMOCLAW_INFERENCE_BASE_URL/models" -H "Authorization: Bearer $NEMOCLAW_API_KEY" | grep -o "\"id\":\"[^\"]*\"" | head -20
```

<Callout type="warn" title="If it fails">
<strong>401 / Unauthorized</strong> → wrong or expired key. <strong>404</strong> → the base URL probably shouldn't (or should) end in <code>/v1</code> — match your provider's docs. <strong>Connection error</strong> → check the host name. Fix <code>.env</code> and re-run Step 2 + 3 before moving on.
</Callout>

## Two pieces: a *profile* and a *provider*

OpenShell splits model access into two small concepts:

- A **provider profile** is the *access contract*: which host and port the credential may be sent to, how it's sent (`auth_style: bearer` → an `Authorization: Bearer …` header), the env var that carries it inside the sandbox (`OPENAI_API_KEY`), and the **binaries** allowed to make the call (`node`, `curl`). Profiles are templates — they hold no secret.
- A **provider** is an *instance* of a profile that holds the actual **credential** (your key), stored gateway-side. Sandboxes get access by having the provider **attached**.

So you'll **import a profile** (Step 4), **create a provider** from it (Step 5), and attach it when you create the agent (next lesson).

## Step 4 — Import the provider profile

The workshop rendered a profile for *your* endpoint (its host and port come from `NEMOCLAW_INFERENCE_BASE_URL`). Read it first:

```bash
cat "$NEMOCLAW_INFERENCE_PROFILE"
```

Look for `id: maas-openai`, the `credentials` block (`env_vars: [OPENAI_API_KEY]`, `auth_style: bearer`), one `endpoints` entry (your inference host, port, `protocol: rest`) and the `binaries` list. Now hand it to the gateway — `import` the first time, `update` if it already exists (the lab setup may have imported it for you). An update must carry the profile's current `resource_version`, which guards against two people overwriting each other's change, so we copy it from an `export`:

```bash
P="$NEMOCLAW_INFERENCE_PROFILE_ID"
if openshell provider profile describe "$P" >/dev/null 2>&1; then
  RV=$(openshell provider profile export "$P" -o json | jq -r .resource_version)
  sed "/^id:/a resource_version: $RV" "$NEMOCLAW_INFERENCE_PROFILE" > /tmp/profile-update.yaml
  openshell provider profile update "$P" -f /tmp/profile-update.yaml
else
  openshell provider profile import -f "$NEMOCLAW_INFERENCE_PROFILE"
fi
```

## Step 5 — Create the provider (this is where the key goes)

Create a provider of that type. We pass the key through the **environment** (`--credential OPENAI_API_KEY` with no `=value` reads it from the CLI's env), so it never shows up in your shell history or the process list. From here on *the gateway* holds the key — not you, and not the agent:

```bash
openshell provider get "$NEMOCLAW_INFERENCE_PROVIDER" >/dev/null 2>&1 \
  || OPENAI_API_KEY="$NEMOCLAW_API_KEY" openshell provider create \
       --name "$NEMOCLAW_INFERENCE_PROVIDER" \
       --type "$NEMOCLAW_INFERENCE_PROFILE_ID" \
       --credential OPENAI_API_KEY
```

Flag by flag:

- `--name "$NEMOCLAW_INFERENCE_PROVIDER"` — what you'll call this provider (`default` unless you changed it). Sandboxes reference it by name.
- `--type maas-openai` — the profile id from Step 4: it decides where the key may go and who may send it.
- `--credential OPENAI_API_KEY` — **this is where your key goes.** It's stored gateway-side as a *credential*, never written into the agent.

## Step 6 — Confirm

```bash
openshell provider list
```

You should see your provider with type `maas-openai` and **one credential key**. Only key *names* are ever shown — never values:

```bash
openshell provider get "$NEMOCLAW_INFERENCE_PROVIDER"
```

## Change it later

To **rotate the key** (reference — run it when you actually have a new key). Attached sandboxes get a re-issued placeholder (a new revision) and the old one eventually stops resolving, so restart a running OpenClaw gateway afterwards (step 2 of *Give It a Brain*):

```bash-ref
OPENAI_API_KEY=<new-key> openshell provider update "$NEMOCLAW_INFERENCE_PROVIDER" --credential OPENAI_API_KEY
```

The **model** is not part of the provider any more — it's chosen by the client (OpenClaw's config, next lessons). To point at a different host, edit the profile and re-run Step 4.

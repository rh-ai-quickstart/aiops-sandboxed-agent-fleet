Before you run agent commands, understand the layer that *manages* the agent: **OpenShell**, the sandbox control plane. Everything here is plain `oc` against the cluster — no agent involved yet.

## The OpenShell gateway

OpenShell runs as a StatefulSet. Look at it:

```bash
oc -n "$OPENSHELL_NS" get statefulset,pods,svc
```

Its **Kubernetes compute driver** continuously watches for sandboxes. A healthy gateway logs it every minute:

```bash
oc -n "$OPENSHELL_NS" logs openshell-0 | grep -i "Listing sandboxes" | tail -3
```

`Listing sandboxes from Kubernetes` = the control plane is alive and watching.

## The sandbox API (a CRD)

A “sandbox” is a Kubernetes custom resource — `sandboxes.agents.x-k8s.io`. That's how the platform represents an agent's isolated home:

```bash
oc get crd sandboxes.agents.x-k8s.io
```

### List sandboxes

List the sandboxes in your namespace (the gateway creates them right next to itself):

```bash
oc get sandboxes -n "$OPENSHELL_NS"
```

If you haven't created an agent yet it's **empty** — you build your first in Part IV (an agent like `shifty` only shows here once it exists, as `default--shifty`: the gateway prefixes the workspace name). The point is the *shape*: every agent the gateway makes shows up here as a `Sandbox` CR (`agents.x-k8s.io/v1beta1`) you can inspect with plain `oc` (`oc -n "$OPENSHELL_NS" describe sandbox default--<name>`). That's the whole API surface — a Kubernetes object.

## Policies — what a gateway sandbox may do

An OpenShell-managed sandbox policy is **one YAML file with two halves**: a *dynamic* network section that hot-reloads on a running sandbox, and *static* filesystem + process sections locked in at creation and enforced in the kernel. Click through each part:

<PolicyExplorer />

For sandboxes created through the OpenShell gateway, every section maps to a real enforcement point — nothing here is advisory:

| Layer | Protects against | Enforced by | Runtime change? |
| --- | --- | --- | --- |
| `network_policies` | egress / data exfiltration | CONNECT proxy + OPA, per-binary | ✅ hot-reload |
| `filesystem` | binary tampering, cred theft | **Landlock LSM** (kernel) | ❌ recreate |
| `process` | priv-esc, fork bombs, bad syscalls | **seccomp-BPF** + privilege drop | ❌ recreate |

### See it on your cluster

The repo ships the OpenShell policy your agent will use. Print the real file:

```bash
cat ~/nemoclaw-openshift-launchable/policies/openclaw-sandbox.yaml
```

It's short — here's the whole thing, and every line is a guardrail:

```yaml
version: 1

filesystem_policy:                       # what the agent may touch on disk
  include_workdir: true
  read_only:  [/usr, /lib, /proc, /dev/urandom, /app, /etc, /var/log]
  read_write: [/sandbox, /tmp, /var/tmp, /dev/null]

landlock:
  compatibility: best_effort             # enforce the FS rules via the kernel (Landlock LSM)

process:
  run_as_user: sandbox                   # the agent runs unprivileged, never root
  run_as_group: sandbox

network_policies:                        # a MAP of named egress rules — deny-by-default
  in-cluster-registry:                   # the workshop's private npm registry (skills)
    name: in-cluster-registry
    endpoints:
      - { host: registry.openshell.svc.cluster.local, port: 4873, access: full, protocol: rest, allow_encoded_slash: true }
    binaries:
      - { path: /usr/bin/node }          # ONLY node/npm may use this rule
      - { path: /usr/local/bin/node }
      - { path: /usr/bin/npm }
      - { path: /usr/local/bin/npm }
  npm-registry:                          # public npm, for plugin dependencies
    name: npm-registry
    endpoints:
      - { host: registry.npmjs.org, port: 443, access: full, protocol: rest, allow_encoded_slash: true }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node }, { path: /usr/bin/npm }, { path: /usr/local/bin/npm } ]
  websearch:                             # DuckDuckGo, for the web-search tool
    name: websearch
    endpoints:
      - { host: duckduckgo.com, port: 443, access: full }
      - { host: html.duckduckgo.com, port: 443, access: full }
      - { host: lite.duckduckgo.com, port: 443, access: full }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node } ]
```

Now read it block by block:

- **`version`** — the policy schema version. Just `1`.
- **`filesystem_policy`** — the agent's view of the disk. `read_only` covers the system dirs (so it can't tamper with binaries or configs); `read_write` is **only** its home (`/sandbox`), `/tmp`, and `/dev/null`. Anything not listed — `/workspace`, the host filesystem — simply isn't there for the agent.
- **`landlock`** — those filesystem rules aren't advisory. They're enforced by **Landlock**, a Linux-kernel security module, so even a compromised agent can't step outside them.
- **`process`** — the agent runs as the unprivileged `sandbox` user, never root (backed by seccomp-BPF + privilege drop).
- **`network_policies`** — the heart of it: a **map** of named rules, deny-by-default. Each rule pairs **endpoints** (the host + port the agent may reach) with **binaries** (which executables may use that egress). Here there are three — the in-cluster skill registry, public npm, and DuckDuckGo — all for `node`/`npm` only, and nothing else. (In a shared lab the registry host carries your own namespace, <code>registry.<Ns which="openshell" />.svc.cluster.local</code>; the workshop rewrites it at startup.)

Read it as one sentence: *"`node` may open `:443` to `duckduckgo.com` — `curl` may not, and nobody may reach anywhere else."* That **per-binary, per-host** egress is what stops a prompt-injected agent from exfiltrating data through an unexpected channel — a deny-all firewall with tiny labelled doors.

<Callout type="note" title="Where's the model endpoint?">
Notice the policy has <strong>no rule for inference</strong>. That access comes from a <em>provider</em> attached to the sandbox (last section below): its profile adds the inference endpoint to the sandbox's <em>effective</em> policy — for the listed binaries only — and brokers the key. Without the provider attached, a call to the inference host is denied like anything else.
</Callout>

You'll see this exact policy **enforced live** in the next lesson (on a throwaway sandbox) and again when you build your agent in Part IV — `openshell policy get <name>` prints the *effective* policy (add `--full` to include provider-composed rules). The gateway compiles this file into kernel-level (Landlock/seccomp) and proxy-level (OPA egress) rules.

<Callout type="tip" title="The iterate loop">
For a gateway-created sandbox, start in <strong>audit</strong> mode (violations logged, not blocked), watch <code>openshell logs &lt;name&gt;</code> for denials, add the endpoints you actually need to <code>network_policies</code>, then flip to <strong>enforce</strong>. Tighten without downtime — network rules hot-reload.
</Callout>

<Callout type="note" title="Who reconciles the sandbox?">
The agent-sandbox <strong>controller</strong> (kubernetes-sigs/agent-sandbox v1.0.3, installed once per cluster) turns the <code>Sandbox</code> CR into a real pod, under the namespace's RBAC + Security Context Constraints — sandboxes run under the default <code>restricted-v2</code> SCC, no privileged grant. OpenShell is the broader control plane: the gateway, plus a <strong>supervisor</strong> per sandbox (you'll see an <code>os-supervisor-…</code> pod next to each one).
</Callout>

## Credentials — providers and placeholders

The gateway is also where secrets live, as two control-plane objects you'll use in Part IV:

- A **provider profile** — the access contract for a kind of credential: which **host + port** it may be sent to, how (e.g. `Authorization: Bearer`), the env var that carries it in the sandbox (`OPENAI_API_KEY`), and which **binaries** may send it. No secret inside.
- A **provider** — an instance of a profile holding the actual **credential** (your key), stored gateway-side. You **attach** it to sandboxes.

```bash-ref
openshell provider profile import -f "$NEMOCLAW_INFERENCE_PROFILE"      # the access contract
OPENAI_API_KEY=… openshell provider create --name default \
  --type maas-openai --credential OPENAI_API_KEY                          # key held by the gateway
openshell sandbox create … --provider default                            # attach at creation
openshell provider list                                                  # never prints key values
```

These are shown for reference — you'll actually run them in **Part IV**, not here. Inside an attached sandbox, `$OPENAI_API_KEY` holds only a **placeholder** (`openshell:resolve:env:…`). The agent calls your real endpoint with it; the supervisor's egress proxy sees the placeholder and swaps in the real key — only toward the profile's host, only from its binaries. Two consequences, both good: the agent **never holds your key**, and a stolen placeholder is worthless anywhere else.

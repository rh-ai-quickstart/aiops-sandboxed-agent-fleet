You created `shifty` with `openshell sandbox create`. Each sandbox is reconciled into a **pod** — but a *sealed* one. To run *agent* commands you go **into the sandbox**, and there are two ways in that land in two different worlds. Understanding the difference is understanding OpenShell.

## A sandbox is a pod

```bash
oc -n "$OPENSHELL_NS" get pod default--shifty -o wide
```

It's a normal pod (named `default--shifty` — the gateway prefixes the workspace) with an `agent` container. Its supervisor runs in a companion `os-supervisor-…` pod. And the OpenClaw agent runs inside the **OpenShell sandbox runtime** in that container: a Landlock-restricted filesystem, and every network connection checked against the policy before it leaves.

## Two ways in

**`oc exec`** lands in the `agent` container directly — outside the gateway, so nothing it does is checked against the policy or recorded in the audit log:

```bash
oc -n "$OPENSHELL_NS" exec default--shifty -c agent -- sh -c 'echo HTTPS_PROXY="$HTTPS_PROXY"; ls /sandbox >/dev/null 2>&1 && echo "can see /sandbox" || echo "no /sandbox here"'
```

<Callout type="warn" title="Shared lab? Expect Forbidden here">
In a multi-user lab your ServiceAccount is <strong>not allowed</strong> to <code>oc exec</code> into sandbox pods — the command above returns <code>Forbidden</code> (<code>cannot create resource "pods/exec"</code>). That's RBAC doing its job: a raw exec would bypass the gateway, its audit trail and the sandbox seal. Use <code>openshell sandbox exec</code> (next) — it goes through the gateway and lands inside the seal. On a single-user cluster the <code>oc exec</code> works and shows you the outer shell.
</Callout>

**`openshell sandbox exec`** lands in the *agent's* sealed context — Landlock filesystem (`/sandbox`, `/tmp`) and the governed egress proxy. This is where the agent actually lives:

```bash
openshell sandbox exec -n shifty -- sh -c 'echo HTTPS_PROXY="$HTTPS_PROXY"; whoami; pwd'
```

Notice there's **no** `HTTPS_PROXY` in either shell: in OpenShell 0.1.x egress is mediated transparently. Every connection the agent opens is checked against its policy (binary, host and port, then the HTTP request) and logged — `openshell logs shifty --source sandbox` shows lines like `NET:OPEN … ALLOWED … [policy:websearch]`; anything not allowed is refused. The `oc exec` shell sits outside that path: no policy decisions, no audit trail. That gap *is* the seal.

## Run the agent CLI

The `openclaw` binary lives inside the sandbox; run it through the sealed exec:

```bash
openshell sandbox exec -n shifty -- openclaw --help
openshell sandbox exec -n shifty -- openclaw config get gateway
```

<Callout type="tip" title="Mental model">
<strong>OpenShell</strong> manages sandboxes from outside (the control plane: <code>openshell …</code> / <code>oc</code>). <strong>Inside a sandbox</strong> you run the agent's own commands with <code>openshell sandbox exec -n shifty -- openclaw …</code>. Use <code>oc exec</code> only for the pod's outer shell — it bypasses the gateway's policy checks and audit trail, so it's not how the agent sees the world.
</Callout>

<Callout type="rh" title="Why the seal matters">
This is the same isolation that stops a gateway sandbox from reaching the in-cluster Kubernetes API: the agent only egresses through the governed proxy. You can inspect the pod from outside all you like; the agent itself is boxed in. That's what lets you run untrusted agents safely.
</Callout>

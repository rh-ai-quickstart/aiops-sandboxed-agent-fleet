The gotchas we hit so you don't have to. Most are handled by the Helm chart — here's what to check if something's off (run the checks in the shell).

## Can't reach the agent UI on :30789
The agent UI is bridged out of the sealed sandbox by `openshell forward`, run by the workshop pod's `openclaw-forward` sidecar (your shell shares its network). Check the bridge and that the OpenClaw gateway is up inside the sandbox:

```bash
curl -s -o /dev/null -w "OpenClaw UI: HTTP %{http_code}\n" http://127.0.0.1:30789/
openshell sandbox exec -n shifty -- sh -c 'tail -3 /sandbox/gateway.log'   # gateway listening?
```

## Can't reach the gateway
The gateway is an in-cluster Service in your namespace (no public Route). Check that the Service exists, the gateway pod is running, and the CLI is pointed at it:

```bash
oc -n "$OPENSHELL_NS" get svc openshell
oc -n "$OPENSHELL_NS" get pods
openshell gateway list
openshell status
openshell sandbox list
```

If the pod is running but the gateway isn't responding, check its logs:

```bash
oc -n "$OPENSHELL_NS" logs openshell-0 --tail=50
```

## A sandbox never becomes Ready (or shows Completed)
Two classic causes: it was created **without `--policy`** (its supervisor keeps waiting for a policy the gateway doesn't have), or its main command **exited** (e.g. `-- true`), which leaves the sandbox *Completed*. Look at it, then recreate it the right way:

```bash
openshell sandbox list
oc -n "$OPENSHELL_NS" get sandboxes,pods
```

```bash-ref
openshell sandbox delete shifty
openshell sandbox create --name shifty --from "$OPENCLAW_SANDBOX_IMAGE" \
  --policy ~/nemoclaw-openshift-launchable/policies/openclaw-sandbox.yaml \
  --provider "$NEMOCLAW_INFERENCE_PROVIDER" --no-tty --detach -- sleep infinity
```

## The agent gets 401 / can't reach the model
The agent only reaches your endpoint through an **attached provider**. Check the attachment and the provider:

```bash
openshell sandbox provider list shifty
openshell provider list
```

If nothing is attached, attach it and wait until the sandbox has applied it — then restart OpenClaw (only *new* processes receive the credential placeholder):

```bash-ref
openshell sandbox provider attach shifty "$NEMOCLAW_INFERENCE_PROVIDER" --wait
```

## Can't reach the OpenShift console
Check the console Route and pods (in a shared lab the console may not be offered — the workshop hides its link then):

```bash
oc -n openshift-console get route
oc -n openshift-console get pods
```

## OpenClaw asks for device pairing
That's expected — approve it (see [Pair Your Browser](/learn/pairing) in Part IV):

```bash
sbox-openclaw devices list
sbox-openclaw devices approve <REQUEST_ID>   # the Request id from the list above
```

## Image pulls stall ("unexpected EOF")
Check the cluster's network connectivity — this is often an MTU or DNS issue on the underlying infrastructure.

<Callout type="note" title="Helm chart is re-deployable">
The Helm chart is idempotent — fix the cause and re-deploy to reconcile.
</Callout>

Your sandbox is up, but it's empty — no model, no running agent. OpenClaw reads its config from `~/.openclaw/openclaw.json` (inside the sandbox, `HOME` is `/sandbox`). Let's give it a model and start the **OpenClaw gateway** (its Control UI + agent runtime).

## 1. Build the config — pointed at your real endpoint, with a placeholder key

OpenClaw talks to your **real** inference endpoint (`$NEMOCLAW_INFERENCE_BASE_URL`) — but with a **placeholder** API key. When you attached the provider (`--provider` in the last lesson), the sandbox got an `OPENAI_API_KEY` env var whose value is not your key but a reference the supervisor understands. Let's look at it from *inside* the sandbox:

```bash
PH=$(openshell sandbox exec -n shifty -- sh -c 'printf %s "$OPENAI_API_KEY"')
echo "inside the sandbox, OPENAI_API_KEY=$PH"
```

You'll see something like `openshell:resolve:env:v<revision>_OPENAI_API_KEY` — a placeholder, useless outside this sandbox. Note the **revision**: the gateway re-issues the placeholder whenever the provider changes (a rotated key, for example), and an old one eventually stops resolving. So we don't copy it into OpenClaw's config: the config says `${OPENAI_API_KEY}`, and OpenClaw substitutes the sandbox's current placeholder each time it starts. We build the config on the host, then stage it **into the sandbox** — and because the agent is Landlock-confined, we write it through `openshell sandbox exec` (base64, since exec doesn't take multi-line args):

```bash
cd ~/nemoclaw-openshift-launchable
set -a; . .env; set +a
PW="${OPENCLAW_GATEWAY_PASSWORD:-openclaw}"
PH=$(openshell sandbox exec -n shifty -- sh -c 'printf %s "$OPENAI_API_KEY"')
[ -n "$PH" ] || echo "WARNING: OPENAI_API_KEY is empty inside the sandbox — is the provider attached? (openshell sandbox provider list shifty)"
OC=$(jq -n --arg model "$NEMOCLAW_MODEL" --arg pw "$PW" --arg base "$NEMOCLAW_INFERENCE_BASE_URL" \
  --argjson cw "${NEMOCLAW_MODEL_CONTEXT_WINDOW:-65536}" '{
    gateway: { port:30789, auth:{password:$pw}, remote:{ url:"ws://127.0.0.1:30789", password:$pw },
               trustedProxies:["127.0.0.1/32"],
               controlUi:{ dangerouslyAllowHostHeaderOriginFallback:true } },
    agents:  { defaults:{ model:{ primary:("custom/"+$model) } } },
    models:  { providers:{ custom:{ baseUrl:$base,
               apiKey:"${OPENAI_API_KEY}", api:"openai-completions",
               models:[{id:$model,name:$model,contextWindow:$cw,maxTokens:4096}] } } }
  }')
echo "$OC" | jq .   # <- see exactly what we're about to write
openshell sandbox exec -n shifty -- sh -c "mkdir -p /sandbox/.openclaw && echo $(printf '%s' "$OC" | base64 -w0) | base64 -d > /sandbox/.openclaw/openclaw.json"
openshell sandbox exec -n shifty -- openclaw config validate
```

That `echo "$OC" | jq .` prints the exact `openclaw.json` you're staging — it looks like this:

```json
{
  "gateway": {
    "port": 30789, "auth": { "password": "<your gateway password>" },
    "remote": { "url": "ws://127.0.0.1:30789", "password": "<your gateway password>" },
    "trustedProxies": [ "127.0.0.1/32" ],
    "controlUi": { "dangerouslyAllowHostHeaderOriginFallback": true }
  },
  "agents": { "defaults": { "model": { "primary": "custom/<your-model>" } } },
  "models": {
    "providers": {
      "custom": {
        "baseUrl": "https://<your-endpoint>/v1",
        "apiKey": "${OPENAI_API_KEY}",
        "api": "openai-completions",
        "models": [ { "id": "<your-model>", "name": "<your-model>", "contextWindow": 65536, "maxTokens": 4096 } ]
      }
    }
  }
}
```

`Config valid` means OpenClaw accepted it. (`trustedProxies` is for the next lesson: your browser reaches this UI through `openshell forward`, which connects from `127.0.0.1` and passes on the browser's forwarded headers. OpenClaw only accepts those headers from a proxy you list, and otherwise answers `proxy_attribution_required`.) Two more things to notice: `models.providers.custom.baseUrl` is your **real** endpoint, and `apiKey` is `${OPENAI_API_KEY}` — at startup OpenClaw replaces it with the sandbox's **placeholder**, never your key. When OpenClaw (`node`) calls your endpoint, the request leaves through the sandbox's egress proxy; the supervisor sees the placeholder in the `Authorization` header and swaps in the real key — because the provider's profile says that credential may go to *that* host, from *that* binary. Anywhere else, the placeholder stays a placeholder.

You can see the rule the provider added to the sandbox's **effective** policy (your file + provider-composed entries):

```bash
openshell policy get shifty --full | grep -B2 -A8 -i "$(echo "$NEMOCLAW_INFERENCE_BASE_URL" | sed -E 's#^[a-z]+://([^/:]+).*#\1#')"
```

<Callout type="note" title="Why stage through the gateway, not oc cp">
The agent is sealed under <strong>Landlock</strong> — it can only write to <code>/sandbox</code>, <code>/tmp</code> and <code>/var/tmp</code> (system paths like <code>/usr</code> are read-only, everything else is invisible). A file copied into <code>/workspace</code> would be invisible to it — and in a shared lab, <code>oc cp</code> / <code>oc exec</code> into pods is Forbidden anyway. Writing through <code>openshell sandbox exec</code> lands in the agent's real view. Same isolation, everywhere.
</Callout>

## 2. Start (or restart) the OpenClaw gateway

So far the sandbox has just been **idling** — its main process is `sleep infinity`. Now we launch **OpenClaw** inside it, with the config you just wrote — on port `30789` (LAN bind so we can expose it next), password auth.

We start it under `setsid` so it runs in its **own session** and keeps running after this command returns (a plain background process would be killed when the `exec` session ends). It first stops any running gateway by its process name, `openclaw-gateway` — so this same command is also how you **restart** OpenClaw to pick up later config changes (run it again any time):

```bash
openshell sandbox exec -n shifty -- sh -c \
  'cd /sandbox && pkill -f "^openclaw-gateway"; sleep 2; pkill -9 -f "^openclaw-gateway"; setsid nohup openclaw gateway run --port 30789 --bind lan --auth password --password '"${PW:-${OPENCLAW_GATEWAY_PASSWORD:-openclaw}}"' --allow-unconfigured >/sandbox/gateway.log 2>&1 < /dev/null & echo $! > gateway.pid; for i in $(seq 1 15); do grep -qE "\[gateway\] ready|listening on ws" /sandbox/gateway.log && break; sleep 2; done; grep -E "\[gateway\] ready|listening on ws" /sandbox/gateway.log'
```

<Callout type="note" title="Why stop it by name, not `gateway restart` or a PID file?">
There <em>is</em> an <code>openclaw gateway restart</code> (and <code>gateway stop</code>), but they manage an <strong>installed OS service</strong> (systemd/launchd) — this sandbox is a minimal container with no init system, so we run the gateway in the foreground ourselves. A PID file isn't reliable either: OpenClaw renames its process <code>openclaw-gateway</code> and can restart itself under a <strong>new PID</strong> (it does after a plugin install), and a second gateway then refuses to start on the same state directory. So we match the process name from its start, <code>pkill -f "^openclaw-gateway"</code>: it never matches the shell running this command. A gateway stuck mid-restart ignores a normal stop, hence the <code>pkill -9</code> two seconds later.
</Callout>

The line that matters is **`[gateway] ready`** — your agent's Control UI + WebSocket gateway is up on port `30789`, running inside the sealed sandbox. You'll expose it with `openshell forward` in the next lesson.

<Callout type="note" title="What about port 30791?">
You'll also see <code>Browser control listening on http://127.0.0.1:30791</code>. That's a <em>separate</em> helper OpenClaw always starts for browser automation (the Chrome-extension relay) — bound to <strong>127.0.0.1 only</strong>, inside the sandbox, so it's never exposed. Ignore it; your gateway is the <code>:30789</code> one. The <code>security warning</code>, <code>update available</code>, and <code>Chrome extension relay</code> lines are likewise harmless notices.
</Callout>

## 3. Prove the brain works

Have the agent run one turn. The OpenClaw gateway you just started owns the agent's state, so the turn goes **through it** (the CLI finds it on `gateway.port`, 30789) — it sends its thinking to your endpoint, with the placeholder key:

```bash
openshell sandbox exec -n shifty -- sh -c 'cd /sandbox && openclaw agent --agent main -m "Reply with exactly: PONG" --session-id smoke'
```

You should get back `PONG`. If it answers, the whole chain is live: the agent reached the model **without ever holding your key**.

<Callout type="note" title="Why not --local">
<code>openclaw agent --local</code> runs the agent embedded, but OpenClaw refuses it while a gateway owns the same state directory (<em>"A Gateway is running for this state directory … Run without --local"</em>). Without <code>--local</code> the CLI targets the gateway on <code>gateway.port</code> — that's why the config sets <code>port: 30789</code> (the default would be 18789). The fleet agents in Part VI run no gateway, so they do use <code>--local</code>.
</Callout>

<Callout type="rh" title="The privacy boundary, made real">
That reply travelled: agent (<code>node</code>, holding only the placeholder) → the sandbox's egress proxy → the supervisor checks the effective policy (your endpoint, allowed for <code>node</code> by the provider's profile) and swaps the placeholder for your real key → your inference endpoint → back. The agent never saw the key, and the key can only ever reach the host the profile names. Next: open the UI in your browser.
</Callout>

**OpenShell** is what makes "run an autonomous agent *safely*" real. The pitch in one line: **to be useful, agents need access; to be safe, they need Zero Trust** — and OpenShell is the runtime that gives you both. It's not a single process; it's a gateway plus a set of guardrails, sitting on an open-source Kubernetes primitive.

## Inside the runtime

Two paths run through OpenShell: the **agent path** (how an agent comes alive and does work) and the **guardrail path** (what bounds it). Toggle between *what each piece is* and *what it becomes on Kubernetes*, and click any component:

### The agent path
- **Gateway** — the control plane (gRPC :8080). It allocates sandboxes, mints each a scoped identity, and hosts the policy engine + the credential store (providers). On K8s it's a StatefulSet whose *compute driver* watches the Sandbox CRD.
- **Sandbox Supervisor** — delivered by the gateway to **every** sandbox (on Kubernetes you'll see an `os-supervisor-…` pod per sandbox). It builds the agent's isolated network namespace, exchanges a bootstrap token for a sandbox JWT, relays exec/SSH, enforces sandbox-side policy, and swaps credential placeholders for real secrets on egress.
- **Agent Harness** — the agent itself (Definition · Memory · Skills), wrapped by the supervisor in every gateway-created sandbox. Your `shifty` agent is exactly this: the OpenClaw image + a `.md` workspace, running as an `agents.x-k8s.io` `Sandbox` the gateway manages.
- **Sub-Agents** — focused agents the harness can spawn, each its own sandbox with its own identity and policy.
- **Accelerated Tooling** — what the agent reaches *through the guardrail*: filesystem, search, Omniverse/CAD, models — via API, CLI, or MCP.

### The guardrail path
- **Policy Engine + Validator** — deny-by-default. Per binary, which hosts/methods/paths are allowed; a draft validator can propose additions for a human to approve.
- **Network Guardrail** — kernel-level, per-binary egress (`git → github.com ✓`, `curl → anywhere ✗`). Stops exfil through unknown channels; instant, no restart on change.
- **Credential brokering (providers)** — secrets live in the gateway as *providers*, typed by *provider profiles* (allowed host, port, binaries). An attached sandbox sees only a **placeholder** (`openshell:resolve:env:…`); the supervisor injects the real key on egress, only to the profile's endpoint. **This workshop uses exactly this:** you register your endpoint + key as a gateway *provider* (Part IV) and attach it to your agent, so the agent calls your real endpoint yet never holds your key.
- **Model** — where inference runs. Here, a remote OpenAI-compatible endpoint (no local GPU); in a GPU cluster, an in-cluster vLLM.

<Callout type="note" title="Why a runtime (not just a prompt)">
Safety as a system prompt is a suggestion; safety at the <em>network and process layer</em> is enforced. Even if the agent is prompt-injected, the guardrail only lets its binaries reach the hosts and paths you allowed.
</Callout>

## On Kubernetes — the real deployment

### Five enforcement layers

Every sandbox is bounded at five independent layers — some locked at creation, some hot-reloadable:

| Layer | Protects against | Enforcement point | Change at runtime? |
| --- | --- | --- | --- |
| **Network** | egress / data exfiltration | CONNECT proxy + OPA policy (per-binary) | ✅ `openshell policy set` |
| **Filesystem** | binary tampering, cred theft | Landlock LSM (kernel) | ❌ recreate sandbox |
| **Process** | priv-esc, fork bombs, bad syscalls | seccomp-BPF + privilege drop | ❌ recreate sandbox |
| **Credentials** | key exposure / exfiltration | provider profile + placeholder swap on egress | ✅ `openshell sandbox provider attach` |
| **Gateway** | unauth access, transport tampering | mTLS / OIDC (here: in-cluster only, no public Route) | config |

That's the defense-in-depth for OpenShell-governed sandboxes: even a fully prompt-injected agent is boxed in by the kernel and the proxy, not by a prompt. On top, OpenShift contributes its own half of the story — SCCs, pod security settings, and NetworkPolicy — the cluster-native guardrails every sandbox inherits.

<Callout type="note" title="Where this deployment simplifies">
CPU-only, remote inference instead of a local model, and an unauthenticated plaintext gateway reachable <strong>only inside the cluster</strong> (no public Route) instead of mTLS/OIDC. The <em>shape</em> is identical to a full production deployment — fewer optional add-ons.
</Callout>

## The foundation: agent-sandbox (the SIG project)

The bottom layer is community Kubernetes: the `Sandbox` CRD (`agents.x-k8s.io`) and its controller come from **[kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)**. OpenShell adds the gateway, supervisor, credential brokering, and policy *on top*. That's why `oc get sandboxes -n "$OPENSHELL_NS"` works with plain `oc` — they're standard Kubernetes objects.

<Callout type="note" title="Version detail that matters">
The gateway (OpenShell <strong>0.1.6</strong>) speaks the <code>agents.x-k8s.io/v1beta1</code> Sandbox API, so we install agent-sandbox <strong>v1.0.3</strong> — the release OpenShell 0.1.6 is tested against. The gateway and the controller must agree on the API version: an older <code>v1alpha1</code>-only controller would leave gateway-created sandboxes stuck before <code>Ready</code>. The CRD and its controller are cluster-wide and installed once; every gateway (one per attendee in a shared lab) uses them.
</Callout>

## How you reach the gateway

Inside the cluster the gateway is a Service, `svc/openshell:8080`. Your lab shell runs **inside the cluster** (it's the workshop pod), so the `openshell` CLI is pre-registered against that in-cluster endpoint — `http://openshell.<namespace>.svc.cluster.local:8080`:

```bash
openshell status
```

<Callout type="note" title="Why no public Route?">
This gateway accepts unauthenticated clients, so it is deliberately <strong>not</strong> published on an OpenShift Route: only workloads inside the cluster (your lab shell, the workshop's API) can reach it, and in a shared lab a NetworkPolicy keeps other attendees out of your namespace. A production gateway would use mTLS or OIDC and could then be exposed safely.
</Callout>

## Drive the gateway from the CLI

`openshell status` is just the start. The CLI is how you'll do everything — see the verbs:

```bash
openshell --help
```

See which gateways the CLI knows about — you're pointed at the one we registered, `cluster`:

```bash
openshell gateway list
```

And list the agents running on it:

```bash
openshell sandbox list
```

If you haven't built an agent yet, this is **empty** — you create your first one in **Part IV**. (If you do see one like `shifty`, it's simply been created already.) Once a sandbox exists, you reach into it **through the gateway** with `openshell sandbox exec` — audited and policy-enforced, not a raw `kubectl exec` — and that's how you'll run commands inside your agent (including its own `openclaw` CLI) in Part IV.

Part III (next) goes deeper on the control plane and the policy model, with a throwaway sandbox to play on, so you understand every piece before you build for real.

Because the gateway is just gRPC, *anything* that speaks it can drive the fleet — the `openshell` CLI you just used, the companion `openshell-ui` web console, or live panels wired straight into this workshop site from the gateway API.

<Callout type="note" title="Two things both called &quot;gateway&quot;">
You'll hear "gateway" twice: the <strong>OpenShell gateway</strong> (control plane, :8080, reached in-cluster) and the <strong>OpenClaw gateway</strong> (the agent's own control UI, :30789, inside the sandbox). Different things — keep them straight.
</Callout>

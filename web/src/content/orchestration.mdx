You just watched the fleet investigate. There's no magic in it — it's a small orchestrator in
this very website ([`/api/orchestrate`](/learn/incident-lab)), about 130 lines. This page shows
you **all of it**: the plan, the exact prompt each agent gets, how a sealed agent is invoked,
and how the analyst concludes. Nothing here is hidden.

## 1 · A fixed plan — no model call to "plan"

A lot of "agent orchestrators" burn a model call just to decide what to do. We don't. The plan is
**fixed**: one prescribed probe per specialist. The intelligence is in each agent *running and
interpreting* its probe, and in the analyst's synthesis — both reached **through the agent's own
governed model access**, never from the website. Each probe is the exact command the agent runs:

```ts
const TQ = "node /sandbox/.agents/skills/cluster-telemetry/tq.js";
const NS = process.env.DEMO_NAMESPACE;   // your demo namespace — every probe is scoped to it
function buildProbes() {
  const ms = Date.now();
  const range = `&start=${ms - 900000}000000&end=${ms}000000&limit=15`; // last 15 min, newest first (direction=backward)
  return {
    metrics: { url: `https://<thanos>:9092/api/v1/query?namespace=${NS}&query=sum by (code) (rate(shop_requests_total{namespace="${NS}"}[2m]))`,
               hint: "request rate by HTTP code (a 5xx spike is the error rate) + average latency" },
    logs:    { url: `https://<loki>/api/logs/v1/application/loki/api/v1/query_range?query={kubernetes_namespace_name="${NS}"} |= "error"${range}`,
               hint: "the app's recent ERROR log lines (e.g. 'checkout failed: payment provider 503')" },
    events:  { url: `https://<loki>/api/logs/v1/application/loki/api/v1/query_range?query={kubernetes_namespace_name="<openshell ns>",kubernetes_container_name="event-exporter"} |= "reason"${range}`,
               hint: "recent k8s events in the demo namespace — what CHANGED (a scale-down, a deploy)?" },
    traces:  { url: `https://<tempo>/api/traces/v1/dev/tempo/api/search?q={ resource.service.name="shop" && resource.k8s.namespace.name="${NS}" && status=error }&limit=10`,
               hint: "recent ERROR traces — the failing span shows WHERE the request breaks" },
  };
}
```

Every probe is **scoped to your namespace**: Thanos's *tenancy* port (`9092`) only answers for the `namespace=` you pass and checks the caller may read it, Loki filters on `kubernetes_namespace_name`, the events come from an event-exporter dedicated to your demo namespace, and the traces carry a `k8s.namespace.name` resource attribute. In a shared lab, your fleet never sees another attendee's incident.

## 2 · Each agent gets a directive sub-task

Free-form "investigate this" makes a small model wander — read files, hunt for tools, loop until
it blows its context. So each sealed specialist gets a **directive** sub-task that inlines the
exact command. That keeps the tool loop to ~2 calls (run the probe → report), finishing in ~30s:

```ts
const subtask =
 `You are the ${a} specialist of an SRE fleet — read-only, sealed to your one backend.
  Use ONLY the exec tool. Run this EXACT command and report its output verbatim as your
  finding (it returns ${p.hint}), then briefly state what it means and STOP. Do not read
  files, do not use web_fetch or dir_list, and do NOT generate any image.

  Command:
  ${TQ} '${p.url}'

  Incident: ${task}`;
```

## 3 · How a sealed agent is actually invoked

Each step runs **inside the agent's sandbox**, through OpenClaw's embedded agent. The website
never calls a model — the sandbox does, through its attached inference provider (placeholder key, swapped by the supervisor on egress):

```ts
// findings are multi-line, and `sandbox exec` rejects newline args → base64 the message in,
// decode it inside the sandbox.
const b64 = Buffer.from(subtask, "utf8").toString("base64");
await openshell(["sandbox", "exec", "-n", agent, "--", "sh", "-c",
  `openclaw agent --local --json --session-id <uuid> -m "$(printf %s ${b64} | base64 -d)"`]);
```

The probe itself is the **cluster-telemetry skill** (`tq.js`): it shells out to `curl` (an
egress-allowed binary, so the call stays bounded by the agent's single-backend policy) and prints
a *compact* summary so the agent stays focused. OpenClaw's `web_fetch` is blocked for internal
hosts — the skill is how a sealed agent reads `*.svc.cluster.local` without weakening anything.

## 4 · The analyst concludes

The investigators run in **parallel**; when they're all in, their findings go to the
**analyst** (no telemetry access, no tool calls), which reasons over them — combining the error rate,
the error logs, the failing span, and *what changed* according to the events (`payments` scaled to
0) — into a root cause and a recommended remediation:

```ts
const analystPrompt =
 `You are the incident analyst synthesizing an SRE fleet's findings. Reason ONLY over the
  findings below — no tools, no files, no image, and do NOT greet or describe yourself.
  Begin directly with "ROOT CAUSE:" and cite the evidence (error rate, error logs naming the
  failing dependency, the failing span). CRITICAL: ask "what changed?" — if the events
  findings name a recent change (a dependency scaled to 0, a recent deploy) that coincides
  with when the errors began, THAT change is the root cause and the fix is to REVERSE it.
  Never state a change or an error the findings do not show. Then a FINAL line:
  RECOMMENDED_ACTION: <the specific reversal, e.g. "scale the payments deployment back up">`;
```

The whole run is streamed to the page as newline-delimited JSON (`plan` → `step start/done` →
`writer` → `answer`), which is why you see the live timeline, each agent's request, and its
findings appear as they happen. A `heartbeat` event every 15 s keeps the connection alive while a
slow agent is still thinking (cloud load balancers drop connections idle for 60 s).

Small models sometimes skip or mangle the tool call. So after each agent answers, the orchestrator
checks that the finding contains its probe's real output (`status=success …` or `traces=N`); if it
does not, it runs the same probe itself — **inside that agent's sandbox, through its egress
policy** — and uses it as the finding (*verified probe output*), dropping the agent's own text: a
reply without the real output may be invented, for instance the example from its instructions. The
analyst then always reasons over real data, and you can see in the timeline which findings needed
that safety net.

The orchestrator also counts what the probes found: error log lines, error traces, recent events
and the 5xx rate. If every probe answered and all of them are zero, it reports the app healthy
itself (`synthesizedBy: evidence-check`) rather than asking the model, which would otherwise take
"checkout is failing" at its word. Otherwise the analyst gets those counts along with the findings.

<Callout type="rh" title="Why it's built this way">
Two honest constraints shaped this: OpenClaw's <code>web_fetch</code> refuses internal hosts (so
agents read their backend via a <code>curl</code>-based skill), and a small model can't hold a
free-form ReAct loop over large telemetry (so each agent gets one prescribed probe). The result is
<strong>reliable and real</strong> — every agent runs a real query against its real backend, and
the analyst's recommendation comes from live cluster state. Read it, change it, own it.
</Callout>
